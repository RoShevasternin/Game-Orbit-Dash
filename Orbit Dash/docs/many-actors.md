# Багато акторів на екрані: що коштує, а що ні

Документ відповідає на одне питання: **що робити, коли акторів багато** — список,
сітка, сотня сутностей. Усі числа тут заміряні на Redmi 24117RN76E (1080×2400, 60 Hz),
дати в дужках.

## 1. Порядок цін — від найдорожчого

| що | скільки коштує | звідки число |
|---|---|---|
| **FBO-прохід** (перемикання render target) | **≈ 0.19 мс** кожен, незалежно від розміру буфера | 13.09: 8 × `ABlur` по 18 блітів = 20 FPS і на буфері 420², і на 105² |
| **знімок екрана** (`glCopyTexSubImage2D`) | приблизно як FBO-прохід, плюс примусовий resolve тайлів | 14.09: 3 × `ABlurBack` зі знімком щокадру = 53 FPS; ті самі три з кешем = 60 |
| **draw call + bind** | дешево | 14.09: 92 draw + 92 bind = **61 FPS**; 103 draw + 207 перемикань шейдера = **61 FPS** |
| **філ** (пікселі) | помітний лише на повноекранних шарах | 14.09: робочий буфер блюру ×16 менший — той самий середній кадр |
| **ALU в шейдері** | на цих масштабах не існує | `ARoundRect` ≈ 20 операцій на піксель — саме тому в `CLAUDE.md` заборона на FBO-кеш у `VfxImage` |

Головний висновок, який повторився вже тричі різними шляхами: **ціна — це проходи, а не
пікселі й не виклики.** Сто draw call'ів проходять непомітно; сто FBO-проходів убивають
кадр.

Прямий замір цього (14.09, 100 прогрес-барів, у кожного свій прогрес щокадру):

| як зроблено | FPS | draw | bind |
|---|---|---|---|
| `AMask` × 100 — FBO-прохід на кожного | **14** | 303 | 403 |
| `VfxImage` із шейдером × 100 — шейдер на актора | **61** | 103 | 103 |
| одна група, один шейдер, дані у вершині | **61** | **4** | **4** |
| 100 звичайних `Image` з атласу (орієнтир) | **61** | 4 | 4 |

## 2. Що рве батч

SpriteBatch збирає підряд усе, у чого **однакові текстура, шейдер, юніформи й режим
змішування**. Рветься на:

- **іншій текстурі** → тримай усе в одному атласі;
- **іншому шейдері** → став його раз на групу, не на актора (`VfxImage` ставить і знімає
  на кожному — це два флаші на актора);
- **іншому значенні юніформа** → перенеси те, що в кожного своє, у **вершину**: канали
  `color.rgb` вільні, якщо колір задається юніформом (так зроблено в
  `AProgressBatchGroup`, патч 25);
- **зміні blend function**;
- **групі з `isTransform = true`** → два флаші на групу; саме тому в проєкті немає
  transform-груп на сутність (`SizeScaler.kt`, `decisions.md` §6).

**Окремо про `VfxTexture`: це НЕ атлас.** Кожен екземпляр створює власний
`FrameBuffer(RGBA8888, bufW, bufH, false)` зі своєю текстурою (`VfxTexture.createFbo()`);
`VfxTextures` — лише реєстр (список для `update()` і `dispose()`) плюс спільні пул і батч
для самого запікання. Наслідок:

- `Image(tex.region)` × N від **одного** `VfxTexture` — один bind, один батч. Це і є
  сенс запікання («багато однакових, статичних» у `CLAUDE.md`).
- N **різних** `VfxTexture` на екрані — N bind'ів, і вони не батчаться ні між собою, ні
  з ігровим атласом. Чотири-п'ять (як зараз у `SpriteUtil.Msdf`) — байдуже; десятки —
  це вже те, про що §1.
- Потрібні десятки різних запечених фігур в одному батчі — клади їх не в окремі
  `VfxTexture`, а в **спільну** текстуру: або запікай кілька фігур в один буфер і роздавай
  під-регіони, або, як в §5, віддай готовий `Pixmap` в ігровий атлас через
  `texture.draw(pixmap, x, y)` при завантаженні. Сьогодні API першого не вміє — це
  свідомо, бо стільки різних фігур ще не знадобилось.

## 3. Рецепт

1. **Один атлас на екран.** Різні сторінки = гарантований bind між ними.
2. **Жодного `VfxGroup` / `AMask` / `ABlur` на елемент списку.** Це FBO-прохід на кожного.
3. **Шейдер — на групу, не на актора.** Якщо кожному елементу треба своя обробка (прогрес,
   обрізка, відтінок) — один ефект на всіх, а відмінності через вершинні канали.
4. **Статичний композит — запікай.** Кілька шарів, що не змінюються, → один `VfxTexture`
   → далі це звичайна картинка. Правило вибору вже в `CLAUDE.md`.
5. **Не клади сотні акторів усередину `VfxGroup`.** `contentHash()` обходить усе піддерево
   щокадру, щоб вирішити, чи перемальовувати кеш.
6. **Не вішай констрейнти на кожен елемент довгого списку.** `AConstraintLayout` тримає
   снепшоти й перевіряє їх щокадру (це дешево, ~2 порівняння float на дитину), але
   `markDependentsDirty()` — O(вузли × якорі) на кожну зміну розміру. Для сітки з сотні
   плиток дешевше порахувати `x`, `y` самому, як у стенді патча 25.
7. **Пул + відсів.** Тримай живими стільки акторів, скільки видно. `isVisible = false`
   прибирає `draw()`, але **не** `act()` — актор поза екраном усе одно щокадру крутить свої
   Actions. У грі це вже зроблено через пули за `Entity.id` у `GameScreen`.

## 4. Коли FBO-прохід таки потрібен

`VfxGroup` (і `AMask`, `ABlur`, `ABlurBack` як його спадкоємці) існує для одного: коли під
ефектом **сцена, а не текстура**.

- кілька шарів, що блендяться між собою, і результат треба обрізати або розмити;
- живі діти scene2d — рухаються, обертаються, мають власні ефекти;
- результат треба згодувати далі в ланцюг (`ABlurBack`: знімок → блюр → маска).

Якщо під ефектом **одна вибірка з текстури** — FBO не потрібен, це попіксельна арифметика.

Правило на око: **порахуй шари.** Один — шейдер. Сцена — FBO. Статична сцена — запекти
раз у `VfxTexture` і знову шейдер.

Скільки FBO-груп можна тримати живими: **3–4 без просадки, 8 — стеля** (13.09, після
патча 23: 8 × `ABlur` = 56–57 FPS; до патча було 20). Статичні й кешовані не рахуються —
вони коштують один квад.

## 5. Окремий випадок: лідерборд із різними аватарками

Тут маска — не головна проблема. Головна — **різні картинки**: сто різних текстур це сто
bind'ів, хоч із маскою, хоч без. Жоден шейдер цього не лікує.

Суть рішення: **зробити так, щоб маски не існувало на момент рендеру**, а всі аватарки
лежали в **одній** текстурі.

### Як це роблять

1. **Ряди переробляються, а не створюються.** На екрані видно 8–12 рядів — стільки акторів
   і тримай. Прокрутка міняє вміст ряду, а не створює новий (той самий принцип, що пул
   сутностей за `Entity.id` у `GameScreen`).

2. **Динамічний атлас аватарок.** Одна текстура, скажімо 1024×1024 = 256 комірок по 64 px.
   Аватарка приїхала — кладеш її в вільну комірку й запам'ятовуєш `TextureRegion`:

   ```kotlin
   // Один раз на екран
   private val atlasPm  = Pixmap(1024, 1024, Pixmap.Format.RGBA8888)
   private val atlasTex = Texture(atlasPm)          // тримати Pixmap живим, див. CLAUDE.md
   private val circle   = Pixmap(64, 64, Pixmap.Format.RGBA8888)   // кругла альфа, рахується раз

   /** Аватарка приїхала з мережі: обрізати КРУГОМ на CPU і покласти в комірку. */
   fun putAvatar(slot: Int, downloaded: Pixmap): TextureRegion {
       val px = 64
       for (y in 0 until px) for (x in 0 until px) {
           val a = (circle.getPixel(x, y) and 0xFF)               // альфа маски
           val c = downloaded.getPixel(x, y)
           downloaded.drawPixel(x, y, (c and 0xFFFFFF00.toInt()) or ((c and 0xFF) * a / 255))
       }
       val cx = (slot % 16) * px
       val cy = (slot / 16) * px
       atlasTex.draw(downloaded, cx, cy)             // завантаження в підпрямокутник живої текстури
       return TextureRegion(atlasTex, cx, cy, px, px)
   }
   ```

   64×64 = 4096 пікселів на аватарку — це ніщо, і робиться **один раз** при завантаженні,
   а не щокадру.

3. **Далі це звичайні `Image`.** Аватарки — з атласу аватарок, фон ряду, рамки, іконки
   рангу — з ігрового атласу, текст — зі шрифту. Весь список стає 2–3 draw call'ами.

### Якщо форма обрізки різна в різних рядах

Це не змінює схеми: форма — теж просто альфа. Або обрізаєш нею на CPU в тому ж кроці 2
(різні маски для різних рядів — різні `circle`-пікcмапи), або, якщо форма має мінятись на
льоту, лишаєш аватарку необрізаною і берешся за шейдер із патча 25: форма другою текстурою,
а `v_localUV` і канали `color` несуть те, що в кожного своє.

### Якщо іконки свої, а не з мережі

Тоді все ще простіше: вони вже в атласі. Треба кругла обрізка — зроби її **в ассеті**,
при збірці атласу, а не в рантаймі. Маска, якої немає, — найдешевша маска.
