# Журнал рішень: процедурні фігури

Що пробували, що відкинули і **чому**. Головна цінність — причини: без них
наступна спроба піде тим самим колом.

Період: 4–6 вересня 2026.

---

## 1. `Shape` / `ShapeAtlas` / `ShapeTextures` — ВИДАЛЕНО

Рецепт як `data class`, GPU-атлас сторінками 1024², кеш за рецептом. Працювало,
але:

- **розмір фіксований** — рецепт задає роздільність назавжди;
- **три примітиви** (коло, полігон, скруглений прямокутник) і все;
- **заплутано**: розмір у рецепті ≠ розмір на екрані, блюр з'їдає квад,
  ідентичність по всіх полях разом;
- **незмінне**: щоб змінити блюр, треба новий рецепт — а це новий слот в атласі,
  і кеш не витісняється до кінця сесії.

Замінено на `VfxTexture`. Каталог `game/utils/shapes/` видалено.

З нього дожив лише `roundRectFS.glsl` → `RoundRectEffect` → `ARoundRect` (кнопки).
`circleFS` / `polygonFS` / `CircleEffect` / `PolygonEffect` / `ACircle` видалено
7 вересня — див. §6а.

### Дрібниця, яка коштувала вечора

`updateRegion` не компілювався: у `TextureRegion` **немає**
`setRegion(Texture, x, y, w, h)` — такий набір є лише в **конструкторі**.
Правильно двома кроками: `setTexture(tex)`, потім `setRegion(x, y, w, h)`.
Порядок обов'язковий — другий метод ділить на `texture.width`.

## 2. AndroidSVG — ВІДКИНУТО

Ідея: брати SVG з Figma, растеризувати на пристрої під потрібний розмір.

**Не працює для головного випадку.** AndroidSVG (`com.caverock:androidsvg-aar:1.4`,
єдиний живий растеризатор SVG на Android) **не підтримує `<filter>` узагалі** —
тег і всі `fe*` відсутні в переліку елементів парсера, піддерево викидається ще
на етапі розбору, атрибут `filter="url(#…)"` ігнорується. Мовчки, без помилки.
Мейнтейнер, грудень 2023: «probably won't happen anytime soon».

А Figma експортує Layer Blur саме як `<filter>` з `<feGaussianBlur stdDeviation = blur/2>`
і розширює `viewBox` на `blur` з кожного боку. Перевірено емпірично на чотирьох
експортах: коло 84 з блюром 22 → `stdDeviation="11"`, `filter 0 0 128 128`,
корінь 128×128. Тобто AndroidSVG намалював би **різке** коло 84 всередині
прозорого квада 128.

Тінь — те саме: Figma ніколи не пише `feDropShadow`, а ланцюг
`feFlood → feColorMatrix → feOffset → feGaussianBlur → feComposite → feBlend`,
і його теж викидає.

### Супутні пастки, якби все-таки пішли цим шляхом

- **Premultiplied alpha.** `Bitmap` після `Canvas` завжди премультиплікований.
  `setPremultiplied(false)` **не рятує ні за яких умов**: нативно лише перемикає
  прапорець без конверсії пікселів; до рендеру — `Canvas(bitmap)` кидає
  `RuntimeException`; після — тихо ламає `getPixels()`. Єдиний робочий шлях —
  `Bitmap.getPixels(IntArray)` (документовано повертає non-premultiplied) і
  перепакувати в R,G,B,A.
- **Не керована текстура.** `Texture(Pixmap)` після втрати контексту мертва.

### Альтернатива з фільтрами існує, але платна

AmanithSVG — нативний рендерер з **офіційним біндингом для libGDX**
(`com.mazatech.amanithsvg:amanithsvg-gdx`), `SVGTexture extends Texture`, усі 17
фільтр-примітивів у Full-версії. Ціна: нативний C, на Maven лежить лише Lite
(без градієнтів/масок/фільтрів), Full — ліцензія (INDIE безкоштовно з
**обов'язковим сплеш-екраном**, далі €150–15 000), а натіви на Maven вирівняні
на 4 KB і не пройдуть вимогу Google Play про 16 KB page size.

## 3. MSDF — ОБРАНО

Одна текстура тримає будь-який розмір. Конвеєр уже є в проєкті для шрифтів
(`MsdfFont`, `msdf_fill/stroke/shadow`, атласи `mtsdf`, `distanceRange: 32`).

Практика не нова: Valve 2007, msdfgen з 2016 приймає SVG, так роблять Godot 4
(`draw_msdf_texture_rect_region` для будь-якої текстури), Unreal 5.5
(`Font Signed Distance` для UI), Alekon (приціли з SVG).

Покрокова інструкція — `docs/msdf-shapes.md`.

### Що перевірено за першоджерелами (і де я спершу помилявся)

- **`-pxrange` — повна ширина, не досяжність.** `Range(w)` → `lower = −w/2`,
  `upper = +w/2`, край на 0.5. Ефекти дістають **половину** діапазону.
  Світіння 22 текселі → `-pxrange 44`, або асиметрично `-apxrange -24 4`.
  `StrokeEffect.kt` це вже знає: `maxReach = distanceRange * 0.5f - 0.6f`.
- **Точність при великому діапазоні я перебільшив.** Крок 8 біт = діапазон/255,
  похибка ізолінії ≤ діапазон/510 в екранних пікселях: для 132 px на екрані це
  ≤ 0.26 px, субпіксель. «Хвилястість» у Хлумського — про протилежне
  (`pxrange 1`, поля 16×16). Реальна ціна великого діапазону при фіксованих
  `-dimensions` — `-autoframe` **зменшує фігуру** в клітинці.
- **`fwidth` на GLES 2.0 — розширення** `GL_OES_standard_derivatives` (~99 %
  пристроїв), і `textureSize()` там немає — розмір атласу треба юніформом.
  Зате юніформи виходять **лише на атлас** → усе з одного атласу батчиться.
- **`brew install msdfgen` — збірка без Skia.** Бере лише **останній** `<path>`,
  ігнорує `transform`, не конвертує `<rect>/<circle>`, не читає `fill-rule`.
  Тому у Figma — Flatten до одного шляху, а в скрипті `-fillrule evenodd` явно.
- **`msdf-atlas-gen` приймає лише шрифти** — мейнтейнер відмовився додавати SVG
  (Discussion #40). Тому: `msdfgen` на кожен SVG окремо + TexturePacker.

### Межі, які треба пам'ятати

- **Світіння по SDF ≠ гаус.** Спад за відстанню: тонка лінія світить так само
  яскраво, як товстий блок; у кутах ізолінії ламаються; центр не темніє; за
  межею діапазону — різкий обріз. Для світіння «як у Figma» — PNG із
  Figma або `VfxTexture(base = msdf, post = [BlurEffect])`; калібрований
  `CircleEffect` видалено (§6а).
- **Дрібні деталі й тонкі штрихи** обмежені сіткою поля.
- **Одноколірність**: поле — одна форма, один тінт. Градієнти й багатоколірні
  іконки — не сюди.
- **Один `pxrange` на атлас.**
- **Альфа PNG — дані, не прозорість.** Див. нижче.

## 4. TexturePacker для MSDF — критично

Копіювати налаштування з `assets/loader/assets.tps` **не можна**: там стоїть
`Alpha handling = ClearTransparentPixels`, який обнулить RGB там, де альфа 0.
У MSDF альфа — справжній SDF, а RGB у «прозорих» текселях — дані поля.

| опція | для MSDF |
|---|---|
| Alpha handling | **Keep transparent pixels** |
| Premultiply alpha | **off** |
| Trim mode | **None** |
| Filter | **Linear** (білінійна інтерполяція поля і є «вектор») |
| Pixel format | RGBA8888, Png opt level 0 |

Це найімовірніша причина «нічого не працює» при першому запуску.

## 5. TexturePacker CLI — ВІДКИНУТО для MSDF-атласу

CLI-запуск (`TexturePacker msdf.tps`) — платна фіча Essential-режиму. За її
використання TexturePacker **фарбує спрайти червоним**: побайтове порівняння
показало 4087/4096 змінених текселів — поле знищене. GUI-Publish безкоштовний
і чистий, але це зайвий ручний крок.

Рішення: власний `assets/msdf/pack-msdf.py` (полиці, 2 px відступи, текселі
байт-у-байт) + `gen-msdf.command` — подвійний клік робить усе: msdfgen → атлас
у `app/src/main/assets/atlas/`. Перевірено: регіон в атласі збігається з
джерелом на 4096/4096 текселів.

Для звичайних (не-MSDF) атласів GUI TexturePacker лишається як був.

## 6. Модель використання MSDF — ЗАТВЕРДЖЕНО

Питання було: «якщо в SpriteUtil зробити VfxTexture 20×20 з msdf, а потім
покласти в Image іншого розміру — розмиється, як звичайна текстура; як
робити?». Відповідь перевірена на екрані (`docs/msdf-usage.md`):

- **Вектор** (регіон + `MsdfShapeEffect`) — розмір вільний. Один актор →
  `VfxImage`; багато → `AMsdfGroup`, шейдер раз на групу, один draw call.
- **Растр** (`VfxTexture`) — тільки для ефектів. Малювати рівно в розмірі
  запікання; інший розмір → `.resized(w, h)`; ефекти в копії спільні.
- Спільний регіон + зміна параметра ефекту → усі споживачі оновлюються
  наступним кадром. Виміряно чергою кадрів (яскравість 254 ↔ 167).

Що відкинуто: «оновити розмір оригіналу на місці» — це зламало б усіх, хто
його вже малює у старому розмірі. Копія — свідомий вибір.

Виміряно: стенд з 13 фігур (група з 5 + 2 запечені + copy + 2 glow + вектор +
2 довідкові) — draw 12; попередній стенд з 5 `VfxImage` + 2 картинки — draw 14.

### Знахідка: блюр «кривенький» — це крок семплів, не MSDF

`gaussianBlurFS` бере 9 семплів із кроком `radius` текселів (плюс дві зайві
діагоналі). Крок 6 → дірки між семплами → смуги на краю. Рішення без правки
шейдера: світіння на `density = 1` з `radius = 2` — шорсткість 0.50 → 0.00.
Належне рішення на потім — шейдер із σ і семплами по текселю, два проходи.

### Знахідка: MSDF-атлас вантажити синхронно в `GDXGame.create()`

Дотик `assetsMsdf` у `create()` при атласі з хвилі лоадера дає
`lateinit property atlas has not been initialized`. Атлас потрібен усім екранам
(у release першим іде `BrandScreen`), важить кілобайти й ні від чого не
залежить → `loadAtlas()` + `finishLoading()` + `initAll()` у `create()`, як
`BrandScreen` робить із `BRAND`. Перевірено холодним стартом із `BrandScreen`
першим: без крашу, Brand → Loader → далі. `loadAssets()` лоадера підхоплює
MSDF ще раз — `AssetManager` дедуплікує.

### Що лишається з процедурних ефектів після MSDF

| | вердикт | причина |
|---|---|---|
| `PolygonEffect` | **видалено 7 вересня** | гексагон — SVG; користувачів не було |
| `ACircle` / `CircleEffect` | **видалено 7 вересня**; `ABallDecor` → `AMsdfImage(msdf.circle)` | різке коло MSDF робить краще й дешевше; каліброване світіння нікому не було потрібне — числа в §6а |
| `ARoundRect` / `RoundRectEffect` | лишити | `ADefButton` потребує stroke (ghost), `fillAlpha`, динамічний радіус — 9-patch цього не дає; кнопок на екрані одиниці |
| MSDF 9-patch | **відкинуто повністю 7 вересня** | розтяжні панелі — растрові `.9.png` в атласі `_9_PATCH` (`createPatch`), як `panel_coin`. Див. нижче |

Шейдер `msdf_shape` переведено на `d / fwidth(d)` — без цього середина
9-patch (розтяг ×6.7 по X) мала б інший антиаліас, ніж кути.

### 9-patch на MSDF — ВІДКИНУТО (7 вересня 2026)

Пройшли три кроки за один день, кожен наступний скасовував попередній:

1. `ninePatch(region, svgRadius)` з формулою `PX_RANGE/2 + svgRadius×(DIM−PX_RANGE)/DIM`
   — описує лише симетричний rrect, і не перевіряє, чи фігуру взагалі можна тягнути.
2. Явні split, заміряні по полю. Ідея «взяти PNG із Figma в Nine-patch editor» — **не
   працює**: `-autoframe` лишає `PX_RANGE/2` текселів поля і стискає фігуру до
   `(DIM−PX_RANGE)/DIM`, а вписує **bbox шляху**, не `viewBox` — координати Figma й
   регіона не збігаються, сталого перерахунку немає. Мірити треба сам MSDF-PNG по альфі
   (справжня SDF, `0.5` = край). Вимірювач написали й перевірили (`rrect` → 18, як
   формула; `circle`, `star` — 32+32, середини немає).
3. **Рішення: MSDF 9-patch не потрібен.** Кнопки — `ARoundRect` (stroke, `fillAlpha`,
   живий радіус, будь-які пропорції). Розтяжні панелі — растрові `.9.png` в атласі
   `_9_PATCH`, це вже працює. Єдиний сценарій, де MSDF-9-patch виграв би — багато
   панелей однієї орнаментної рамки в одному батчі — у грі не передбачається.

Наслідок: `ninePatch`, `rrect_patch`, `msdf.rrect`, `rrect.svg`, `DIM` видалено;
`msdf_shape.glsl` лишається на `d / fwidth(d)` — це правильно й без 9-patch (обертання,
нерівномірний масштаб).

### 6а. Калібрований блюр кола — ВИДАЛЕНО, числа збережено (7 вересня 2026)

`CircleEffect` / `circleFS.glsl` / `PolygonEffect` / `ACircle` видалено: єдиний користувач
`ABallDecor` малював **різке** коло, а різке коло MSDF робить краще. Світіння в грі —
PNG (`item_glow`) або `VfxTexture(base = msdf, post = [BlurEffect])`.

Щоб не калібрувати заново, якщо шейдерне світіння «як у Figma» колись знадобиться:

- еталон — експорт із Figma: коло 39 юнітів, Layer Blur 22 (`assets/loader/item_glow.png`,
  252×252, альфа в центрі 0.839–0.841);
- `blur` = Layer Blur один в один; `σ = 0.48·blur` — **уточнено 10 вересня**: по
  еталону коло 100 / blur 68 чистий гаус лягає з `σ = 0.426·blur` (RMS 0.006), див.
  «Світіння: чому radius ≠ Layer Blur» нижче;
- заливка: `fill = c · Φ(1.10·((R − len)/σ − 0.40·σ/R))`, де `Φ(x) = 1/(1+exp(−1.702x))`
  (логістична апроксимація нормального CDF), `c = (1 − exp(−R²/2σ²))^0.70` — саме цей
  множник дає **потемніння центру**, коли блюр співмірний з радіусом; `smoothstep` малює 0.99
  замість виміряних 0.84;
- шейдер давав 0.844 у центрі проти 0.841 в еталоні (0.5 %); чистий гаус — 5 % і ширший хвіст;
- калібровано при `R/σ ≈ 1.9`; на дуже інших пропорціях потрібен новий еталон;
- квад мусить бути більшим за коло на `2×blur` — за межі актора шейдер не малює;
- для полігона те саме з апофемою замість `R`.

### Несиметричні SVG — ПРАЦЮЮТЬ (7 вересня 2026)

Питання: чи можна 20×64, 200×100, чи лише квадрат. Перевірено на `msdfgen 1.13`:
клітинка рахується з `viewBox` (довша сторона = `DIM`, коротша пропорційно, плюс
`PXRANGE`), `-autoframe` вписує з полем рівно 4 текселі з усіх боків:

| viewBox | клітинка | фігура в текселях |
|---|---|---|
| 20×64 | 26×64 | 18×56 |
| 200×100 | 64×36 | 56×28 |
| 64×64 | 64×64 | 56×56 |

`pack-msdf.py` довільні розміри пакував і раніше (полиці за висотою). Обмеження — не
пропорції, а **роздільність короткої сторони**: 200×100 при `DIM 64` дає 28 текселів на
100 юнітів; для великих панелей — більший `DIM`. Округлення `W·k` до цілого дає похибку
пропорцій до пів текселя (20×64 → 2.8 %, на 20 юнітах це 0.6 юніта).

### Поле msdf: усередині актора чи назовні (7 вересня 2026)

Перший варіант — `AMsdfImage.setShapeSize(w, h)`, що робить актор більшим на поле.
**Відкинуто того ж дня** (користувач: «`setSize` працює не так, як хочеться, і
`fillParent` ламається»). Ухвалено: `Image` малює поле **назовні** від своїх меж —
квад більший на `width × (PX/2)/(cell − PX)` з кожного боку, по осях окремо.
`setSize` / `fillParent` / `setScale` / hit-box — про фігуру, як у Figma. Звичайна
група не кліпає дітей; усередині `VfxGroup` поле обріже FBO — там потрібен `bleed`
групи. `VfxImage` отримав параметр `inner`. Клас пройшов через імена `MsdfImage` →
`MsdfBatchImage` → приватний `MsdfInner` → загальний `OverflowImage` (15e), бо той
самий прийом потрібен і для `bleed`.

### `AMsdfGroup` — ВИДАЛЕНО (7 вересня 2026)

Батчила msdf-фігури одним draw call, але вимагала, щоб **усі** діти були msdf-регіонами.
У грі кожна сутність — своя група, де msdf-фігура сусідить із PNG-світінням; плоского
списку msdf-фігур немає ніде. Користувачів — нуль. Разом з нею відпав публічний
`MsdfBatchImage`: без групи він потрібен лише всередині `AMsdfImage`, а публічним
лише провокував узяти його замість `AMsdfImage` й отримати кашу без шейдера.

### Ефекти назовні — `bleed` (7 вересня 2026)

Запитання: як зробити, щоб фігура була рівно у своїх межах, а блюр/світіння виходили
за них, як у Figma. Розглянуто:

- **У шейдері** — не можна: шейдер малює лише пікселі всередині растеризованого квада.
- **`VfxGroup` замість `VfxTexture`** — ні: його FBO орендований з пулу екрана, кеш не
  можна віддати іншим акторам, живе один екран і лише всередині власного `draw()`.
  Це «ефект над своїми дітьми тут і зараз», а `VfxTexture` — «текстура, яку тримають
  інші». Обом потрібне те саме поле.
- **Автоматичний bleed** — спершу відкинули як «магію», але наступне ж питання
  користувача було «а яке значення давати?». Формула детермінована й живе в самому
  ефекті, тож рахувати її руками — робота, яку код зробить точніше. Ухвалено:
  `VfxEffect.reachTexels()`, `VfxTexture` підсумовує ланцюг `post`. Явне число
  лишилось як override — під ефект, чий параметр міняється на льоту (FBO фіксований).

Ухвалено: `bleed` — поле на бік у юнітах, у `VfxTexture` (FBO = фігура + 2·bleed,
`image()` → `OverflowImage`, frame = `Image(region)` розміром `outer*`) і у `VfxGroup`
(камера на `−b..w+b`, результат зі зсувом). Правило розміру на той момент: `≈ 9 × radius / density`
(з патча 17 — `min(4·radius·passes, 4σ) / density`, рахує сам ефект)
(4 проходи по 4 кроки по `radius` текселів). `ABlurBack` / `AMask` — `bleed = 0`.
Перевірено трьома незалежними рецензіями й збіркою в лабораторії (патч 15e).

### Світіння по полю відстаней — ВІДКИНУТО (10 вересня 2026)

Ідея: малювати ореол у самому msdf-шейдері, з поля відстаней — як `StrokeEffect`
малює обводку у шрифті. Спокуса зрозуміла: одна текстура, один draw call, жодного
FBO й запікання.

Не пішли з двох причин, і друга важливіша за першу.

**Ціна.** Досяжність ефекту по полю — `pxrange / 2` текселів. У нас `PX_RANGE 8`,
тобто 4 текселі, — на світіння не вистачає. Треба генерувати фігури окремо, з
`-apxrange -24 4` (24 текселі назовні, 4 всередину) і `DIM 128`: клітинка більша,
бо `-autoframe` при широкому діапазоні зменшує саму фігуру в комірці. А `pxrange`
— **один на атлас**, тож це другий атлас поруч із наявним, зі своїм шейдерним
юніформом і своїм батчем.

**Результат.** Навіть заплативши, отримали б не те, що хочемо: світіння по SDF —
спад за відстанню, а не гаус (див. «Межі, які треба пам'ятати» вище). Тонка лінія
світить як товстий блок, у кутах ізолінії ламаються, центр не темніє, за межею
діапазону — різкий обріз.

Ухвалено: світіння лишається **ефектом над текстурою** —
`VfxTexture(base = msdf.x, shape = msdf.effect, post = listOf(BlurEffect(…)))`
або готовий PNG `item_glow` з атласу лоадера. Перевірено на пристрої: 61 FPS,
ореолу немає.

### Світіння: чому `radius` ≠ Layer Blur (10 вересня 2026)

Скарга: `glow` виглядає гірше за Layer Blur у Figma. Причина — `SpriteUtil.kt`:
`BlurEffect(radius = 68f)`, де 68 — число з Figma, а `radius` — **крок семплів у
текселях**. При `density 3` крок = 22.7 юніта: 9 зсунутих копій кола замість гауса.
Побічно: `bleed` 210, FBO 1968² (15.5 МБ) + ping-pong у пулі ≈ 46 МБ; на 1440p буфер
2624 px — понад ліміт GLES2 2048, клемпа не було.

Заміри показали ще два дефекти самого `BlurEffect`, невидимі при читанні коду:

- **діагональні паси робили еліпс.** Напрямки `(0.383, 0.924)` і `(0.924, 0.383)` — обидва
  в першому квадранті, їхні коваріації додаються: власні значення матриці `2.0 ± 0.71`,
  пляма на 45 % ширша по діагоналі. На знімку «до» — еліпс оком, 0° проти 45° різнились
  на 0.054. H+V уже дають точний 2D-гаус; діагоналі не додавали нічого, крім перекосу;
- **9-tap ядро обриває хвіст на 2.37σ**, де гаус ще має 6 % — кільце на темному тлі.

Еталон: експорт із Figma (`textures/loader/TEST_CIRCLE.png`, коло 100, blur 68, 236 px
при 1x). Фіт чистого гауса: **`σ = 29 = 0.426·blur`, RMS 0.006**, центр 0.774 проти
0.784. Тобто Layer Blur — звичайний гаус, а «чистий гаус — 5 %» із §6а на цій
пропорції не підтвердився; Figma лише обрізає bounds на ~2.3σ.

Розглянуто й відкинуто для цього кроку: повернути `CircleEffect` з §6а (тільки коло, а
світіння потрібне по формі шипа/гексагона); PNG із Figma (під кожен розмір окремий файл,
APK росте — користувач проти).

Ухвалено (патч 17): `BlurEffect` — лише H+V, повторені `passes` разів
(`σ = 1.689·radius·√passes` текселів, `reachTexels = min(4·radius·passes, 4σ)`);
`glow = VfxTexture(100, 100, …, BlurEffect(radius 2, passes 12), density 0.4)`;
`VfxTexture` клемпить буфер під `GL_MAX_TEXTURE_SIZE` пропорційно. Перша спроба
`density 0.2, passes 3` дала ту саму σ з буфера 68 px, але апскейл 15× показав злами
нахилу між текселями (Mach-смуги) — тому тексель дрібніший, σ добирається пасами.
На пристрої: RMS проти еталона **0.008**, 0°/45° — 0.004, GL-пам'ять 119 → 70 МБ,
буфер 134² ≈ 72 КБ.

**Етап 2, того ж дня (патч 18, поглинає 17).** Користувач: «треба повноцінне рішення,
щоб блюр працював як у Figma і було зручно робити такі текстури». Ухвалено:

- `BlurEffect(blur)` — один параметр, Layer Blur із Figma у юнітах; `radius` / `passes`
  прибрані з API. Усередині σ = 0.426·blur, крок ≤ 2, пари H+V повторюються, поки σ не
  набереться;
- `reachTexels()` → `reachUnits()` = `blur`: bounds шару у Figma = фігура + blur на бік,
  гаус там ≈ 0.01. `outer` збігається з фреймом «hug contents» 1:1 (236 для кола 100 /
  blur 68);
- `VfxEffect.preferredDensity()`: `VfxTexture` без явної `density` бере мінімум по
  ланцюгу post — блюру досить σ ≈ 12 теселів (6 — видно злами при апскейлі, 12 — ні);
- піраміда: якщо σ у текселях буфера завелика (явна density, `VfxGroup`, `ABlurBack`),
  буфер ділиться на 2 до σ ≈ 12, блюр там, один білінійний апскейл. `VfxContext`
  отримав `pool` і `density`; `PingPong.of()` — ping-pong над чужими буферами;
  `copyFS.glsl` — copy-шейдер, уся робота в лінійному фільтрі;
- `ABlur.radiusBlur` / `ABlurBack.radiusBlur` → `blur`, ті самі юніти.

Заміряно на пристрої проти `TEST_CIRCLE.png` по 8 напрямках: авто-density — RMS 0.0065,
розкид між напрямками 0.005; density 3 (піраміда, 3 рівні, 708 → 88 px) — RMS 0.0091,
розкид 0.006. Стенд із двома плямами по 236 юнітів на одному екрані перекривався на
47 px — міряти по одній або з відступом.

### `StartActivity` — ВИДАЛЕНО (10 вересня 2026)

Була заведена як обхід «`MainActivity` відкривається по кілька разів на Xiaomi». Справжня
причина — не Xiaomi, а задачі Android: запуск не з іконки (IDE, `adb`, «Відкрити» в
інсталяторі/Play Store) дає задачі кореневий intent без `LAUNCHER`, і наступний тап по
іконці при `launchMode="standard"` кладе нову `MainActivity` поверх старої. Заміряно на
пристрої (патч 21): `standard` без `StartActivity` — 2 екземпляри, `onCreate` ×2;
`singleTask` без `StartActivity` — 1. Отже дублювання зупиняє `singleTask` на
`MainActivity`, а `StartActivity` лише пересилала в неї. Splash вона не малювала
(порожній layout). Захист `isTaskRoot` розглянуто й відкинуто: другий `onCreate` він
фінішить, але `onDestroy` тут чіпає `lateinit adManager` → краш; `singleTask` дає те
саме без оборонного коду. Заразом розширено `configChanges`
(`uiMode|fontScale|density|smallestScreenSize|locale|layoutDirection`): перестворення
Activity — друге джерело «двічі», і саме воно веде до нового `GDXGame` у живому процесі
(див. патч 20).

## 7. Відкриті питання

- **`ABooster.aShape`** — досі `TEMP-арт` (коло з атласу), кандидат на
  шестикутник із MSDF.
- **`item_glow`** — PNG в атласі лоадера, ним користуються м'яч, гем, шип, бустер,
  комета. `SpriteUtil.Shapes` більше немає, тож дубля немає; лишається як є.
- **`ASpike.aShape`** — теж `TEMP-арт` (гем із лоадера). Кандидат на SVG шипа.
- **Комбо** (див. `CLAUDE.md`) — механіка з JSX-прототипу в Kotlin не перенесена.
