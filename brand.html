HOW WE
BUILD

One rule shapes every project in this studio, and it is not about code style. It is about where a new idea is allowed to be born. This page is the canonical copy — every game we make points back here.

01THE RULE

Everything new is built in the prototype first. Nothing new goes straight into the game. We port from the prototype to the engine — never the other way around.

A new feature, screen, UX flow, mechanic, tuned number or sound starts life in the browser prototype — a single-file build we open on a phone in seconds. Only once it has been played and approved does it become an engine patch.

02WHY

It is faster to see. The prototype runs in a browser tab. There is no build, no install, no device cable — the owner opens a link and plays the change within a minute of it being written.

It is faster to write. One file, one language, no asset pipeline. Ten iterations of an idea cost less in the prototype than one in the engine.

The prototype is the reference, the game is its copy. This is the real reason. Anything added to the engine behind the prototype's back is something the prototype does not know about — and the moment that happens the two drift apart. Our parity checks compare the engine against the prototype frame by frame and value by value; a divergence that was never a decision is the most expensive kind of bug we have, because nothing is wrong, the two answers are simply different.

03THE LOOP

  1. Build it in the prototype. Fully, not as a stub — real layout, real states, real animation and sound. The prototype is a reference, so it has to be good enough to copy.
  2. Bump the build tag and publish. Every publish gets a version, so it is always obvious whether the tab is showing the new one.
  3. Play it. Automated walkthroughs catch the regressions; the owner plays the link and decides. Rejected here costs nothing.
  4. Port it to the engine and re-run the parity checks until the game matches the prototype.

04WHERE THE RULE DOES NOT APPLY

The prototype is a web page. Some things have no counterpart there and belong to the engine by nature — these go straight into the game, no detour:

  • the port itself, and fixing a divergence — the prototype is right, the game catches up;
  • platform and build: Gradle, manifest, signing, release artifacts;
  • services: ads, analytics, crash reporting, leaderboards, store review;
  • performance and rendering: frame pacing, shaders, pooling, GL context loss;
  • engine tests, documentation, store and marketing material.

Unsure whether something is new work or a port? Ask. Guessing is how the two copies drift.

06FOR OUR OTHER PROJECTS

This page is the studio-wide copy, so a project that cannot see the game repository can still read the rule. Paste the block below into a new project's own rules file and keep the link, so there is one source of truth and not a dozen paraphrases.

## Як ми працюємо — правило студії Lewydo

**Спочатку прототип, потім перенос. Нічого нового одразу в грі.**
Нова фіча, екран, UX, механіка, число чи звук — спершу в прототипі,
прогін і тест у браузері, і лише потім патч у код гри.

**Прототип — еталон, гра — його копія, не навпаки.** Зроблене в грі
в обхід прототипу прототип не знає → паритет ламається.

Просять щось **нове** напряму в код гри — **спершу нагадати це правило**,
не кидатись робити. Наполіг — робити, але прямо сказати, що прототип
розійдеться, і запропонувати дозаписати зміну в прототип окремим кроком.

Правило не про все. Платформа і збірка, сервіси (реклама, аналітика,
краш-репорти, лідерборди), продуктивність і рендер, шейдери, тести рушія,
документація й market — цього в прототипі немає, тут одразу гра. Сам
перенос і виправлення розбіжності з прототипом — теж гра.
Не зрозуміло, нове це чи перенос — питати.
